## Usage

Normal engine construction with a native plant and combined_cycle_runtime may opt into ongoing paper checkpoints using recovery_account_id='ACCOUNT'.
For explicit shutdown, call engine._checkpoint_morning_recovery(account_id='ACCOUNT', timestamp=exchange_timestamp).
Construct a fresh engine with matching identity and the SAME lifecycle database, then call engine._reconcile_morning_startup(account_id='ACCOUNT', broker=authoritative_broker).
A paper broker in the fixture restores an external simulated broker snapshot first. A Kite adapter must receive an account-scoped StateRecoveryJournal and valid account session. Never restore broker truth from local lifecycle records as though those were authoritative broker inventory.

The method returns prepared=true and admissions_allowed=false only after position comparison and verified protection requests. Failures leave admissions halted and do not install partial fleet/open-position state. A protection write may remain active if a later check fails; recovery does not blindly cancel or repeat it.

## Remaining release gates

This is not a seamless resume executor. Stock PA/chart/MPC PID caches and baselines, ECS state, full native electrical/lockout state and event/data cursor reconstruction remain unfinished. The external execution runner is still paper-only; installing a Kite adapter does not convert its paper execution semantics into a live executor. Day-boundary resets and consumed historical bars must be validated before admissions can be released.

Old close-feedback fleet_state rows are intentionally not treated as complete startup checkpoints. boot_checkpoints provide coherent lifecycle/fleet snapshots. This does not turn two independent journals into a distributed atomic transaction; the older deterministic paper-prefix recovery path remains separate.

Active GTT readback verifies a broker-hosted contingent LIMIT instruction, not guaranteed liquidation. An already-breached stop blocks a new placement and requires the protective execution/reconciliation path. Unknown submissions require explicit reconciliation. Triggered/partially filled/rejected GTT orders require ongoing order/position reconciliation. Corporate actions, circuit limits, availability, and delivery authorisation must be checked in the live release fixtures.
